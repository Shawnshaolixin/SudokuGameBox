# 9-4 热更真机验收复盘：热更组件丢失问题从症状到闭环的完整链路

> 时间：2026-09-02（Phase 9 v1.1 HybridCLR 热更新,分支 dev/phase9）
> 验收项：9-4 Addressables Remote Catalog 真机闭环（10 文档 §16.5）
> 结论：**用户真机全流程检查"功能正常"——主页/难度弹窗/数独对局棋盘渲染/按钮响应/返回全部可用,9 条真机踩坑全部定位修复闭环。**

本复盘回答一个问题：**"主页渲染正常,进数独对局页棋盘不渲染、按钮全无响应"** 这个现象,从怀疑资源、怀疑网络、怀疑热更链,到最后定位为一个架构级缺陷并修复,中间到底做了什么、靠什么证据一步步收敛。

---

## 1. 现象（用户的原始描述）

- 主页（MainMenuView, AOT 程序集,随主包序列化）渲染正常、点击正常。
- 点进数独对局页（GameplayView, **热更程序集** Box.HotUpdate.Sudoku）后：
  - 棋盘**缺失**——棋盘是运行时纯代码生成的（BuildBoardCells,无外部资源）；
  - **所有按钮无响应**——onClick 是 OnCreate 里绑的；
  - 其余静态 UI（标题/工具条/数字盘/返回按钮）**全部正常渲染**；
  - 日志**零报错**。
- 特征一句话：**壳正常、芯没有、还不吭声。**

## 2. 排查过程：排除法逐层收窄

| 轮次 | 怀疑方向 | 验证手段 | 结论 |
|---|---|---|---|
| 1 | 热更链没通(dll 没装载)? | logcat 抓热更链日志 | ❌ 排除：5×AOT metadata + 2 dll + overrides v1.1.0 **全部装载成功**(~0.6s),类型已进 AppDomain |
| 2 | Addressables 资源问题(棋盘贴图/字体)? | 与现象对账 | ❌ 排除：棋盘为纯代码 UGUI(无外部资源),且**静态 UI 正常** = 资源管线是通的 |
| 3 | 组件没挂上(Awake/OnCreate 没跑)? | 现象逐条对账 | ✅ 收敛：棋盘=OnCreate 生成、按钮=OnCreate 绑定、其余静态 UI=场景直接序列化 —— **全部指向"GameplayView 组件从未 Awake"** |
| 4 | 为什么静默丢失? | 构建产物解剖 + HybridCLR 官方文档 | ✅ 定论（见下节） |

## 3. 根因定位：一条完整的证据链

**结论先行：热更视图组件直接序列化进了非 AB 场景引用的 prefab,v1.1 构建剥离热更程序集后,组件在真机反序列化时被 Unity 静默丢弃。**

证据链（每环独立验证,最终闭环）：

1. **构建期事实**：v1.1 打包走 HybridCLR `FilterHotFixAssemblies`,把热更程序集（Box.HotUpdate.*）从主包 AOT **物理剥离**——主包里根本没有这些类型。
2. **APK 解剖（排除法关键一步）**：解开 APK 看 `ScriptingAssemblies.json`,第 181/182 项**仍含热更 dll 条目**（HybridCLR 官方 PatchScriptingAssemblyList 生效,让 IL2CPP 认识热更程序集、不裁剪其 AOT 依赖）。→ 说明"dll 注册"没问题,剥掉的是 **MonoScript 静态脚本表**之外的东西。
3. **机制推导**：Unity 资源反序列化按 **构建期烘焙的 MonoScript 表**（脚本名 ↔ GUID/FileID）把组件还原成实例。热更组件**不在表内**（dll 是运行时才 Assembly.Load 的）→ IL2CPP 找不到目标类型 → **静默丢弃整个组件**（序列化数据没了、Awake 不执行、无任何报错——Unity 对未知脚本的默认行为是忽略并打 missing-script 占位）。
4. **官方文档确认**：HybridCLR 明确——热更脚本挂 prefab/场景,仅 **Addressables AB 打包的资源**能正常还原（AB 含独立脚本表）；**Build Settings 里的非 AB 场景必丢**；官方唯一"无限制"路径 = **Assembly.Load 之后用代码 AddComponent**。
5. **真机实锤（修复轮最后一次抓到的显式证据）**——此前一直没看到"missing script"日志,是因为丢组件时 Unity 只打一条 warning,且用户在崩溃前已把窗口滑过；复测时 logcat 抓到：
   ```
   22:31:54 The referenced script (Box.HotUpdate.Sudoku.GameplayView) on this Behaviour is missing!
   22:31:54 [HotViewBinder] 运行时附加热更视图: Box.HotUpdate.Sudoku.GameplayView
   ```
   第一行是 Unity 官方确认组件丢失,第二行是修复代码把组件挂回——一前一后,根因与修复同框实锤。

**为什么编辑器/测试测不出**：编辑器全量编译（不过滤热更程序集）、IL2CPP 脚本表是构建期概念 → 编辑器里组件序列化还原一切正常。这类缺陷**只存在于 v1.1 真机**,且**静默**,常规冒烟根本碰不到——这是热更新架构里最阴的一类坑。

## 4. 修复方案：AOT 视图桥（用户拍板,方案 A）

三种候选方案对比：

| 方案 | 做法 | 否决/通过理由 |
|---|---|---|
| A. AOT 桥（**采用**） | 视图 prefab 根挂一个 AOT 程序集的 `HotViewBinder`(Box.UI),序列化记录视图类型全名;运行期若根上没有 UIView(说明序列化组件已被剥)则 AppDomain 解析类型 + `AddComponent` 挂回 | 单一代码路径、prefab 一次改造全模式共用、无资源重排、无启动时序依赖、v1.0/编辑器幂等空转 |
| B. 热更脚本打包进 AB | 把 GameplayView 等也打进 Addressables AB,让 AB 独立脚本表兜底 | 场景引用链重排风险大;Gameplay.unity 场景内的 PrefabInstance 引用 AB 资源,编辑器/构建流程复杂化;UI 模块未走 AB |
| C. ModuleLoader 场景内 AddComponent | 启动时定位场景里丢失组件的根,统一补挂 | 桥本身就要做类型解析;集中式扫描依赖"先找到再挂"的时序,不如就地 Awake 里同步补挂干净 |

方案 A 的两个设计点值得记录：

- **幂等判断**：`GetComponent<UIView>() != null` 就视为达成——v1.0/编辑器下组件正常序列化,桥直接空转,零副作用;**同一份 prefab 双模式共用**,不需要两套资产。
- **时序兜底**：热更 dll 通常启动后 1~2s 才装载。桥在 Awake 首试,类型未就绪时**逐帧重试 10s**(MaxRetryFrames=600 @60fps),到达上限打 warning（静态 UI 可见但不响应,提示是热更没装载而不是桥坏了）。

**架构纪律（写进本 repo 的热更开发规则）**：
> 热更 UIView 组件永不直接进 prefab/场景;非 AB 场景引用一律经 HotViewBinder AOT 桥运行时附加。
> 后续新玩法（如 19 文档水排序）的视图组件直接遵守此纪律,不要再踩一遍。

## 6. 修复轮上被再次绊倒的坑（同样只活在真机/产物链路里）

修复本身一次过,但"让真机验证跑起来"的过程又踩了 3 个坑——都值得记:

### 坑⑧'：metadata 陈旧（改 AOT 代码后必须重跑 GenerateContent）

- **症状**：换新 APK 后热更链报 `[HotUpdate] 装载 AOT 元数据 Box.UI 失败: ...`（Consistent 模式 `metadata type not match`）。
- **根因**：本次修复首次改动 **AOT 白名单程序集**（Box.UI 新增 HotViewBinder）。HybridCLR Consistent 模式要求远程 AOT metadata **与包内剥离后的 dll 逐字节一致**；而 BuildV11Apk 流程的 GenerateAll 之后**不自动重跑 GenerateContent**(手动/发布步骤),远程内容仍是旧 metadata(07:58, 41984B),包内已是含 HotViewBinder 的新 strip 产物(43520B)→ 逐程序集校验失败。
- **修复**：补跑 `GenerateContent → Phase9Publish.BuildAll` 重建 ServerData → 新 bundle `7387a82a` → 重部署。
- **教训**：**改了 AOT 白名单程序集(Box.UI 等)里的任何代码,必须同步重跑 GenerateContent**,否则远程 metadata 与包不一致——这条要写进构建流程注释。

### 设备缓存坑（Addressables 的 UnityWebRequest Caching）

- **症状**：重建远程内容并重部署后,真机仍 mismatch;服务器访问日志**只收到 catalog 请求、收不到 bundle 请求**。
- **根因**：bundle 下载走 UnityWebRequest 的磁盘缓存（UnityCache/Shared）,旧缓存命中 → app 根本不发网络请求、拿的还是旧 bundle 的旧 hash 内容。
- **修复**：`ClearDependencyCacheAsync` 清不掉（Addressables 已知局限）;`pm clear`/`rm` 在 ColorOS 权限受限 → **卸载重装**才是彻底清场。之后服务器收到完整请求序列 hash → catalog → bundle,热更链全通。
- **教训**：改远程内容后若"怀疑自己改了个寂寞",先查服务器访问日志确认 bundle 请求真的到达;缓存排查优先级高于代码排查。

### 环境噪音（本机代理 / 别名 IP）

- curl 走系统代理(7897),打本机/局域网全是 502/000 → 自测必须 `curl --noproxy "*"` 直连。
- 家庭光猫按网段隔离（手机 192.168.1.x / 电脑 192.168.0.x 不通）→ 给电脑 WLAN 加别名 IP `192.168.1.100`（netsh,持久化）;别名偶发丢失,ipconfig 核对后 netsh 重加。

## 8. 工程经验提炼（可直接用于面试叙事）

1. **"壳正常、芯没有、还不吭声"的三元特征 = 组件生命周期从未执行**,优先查"组件是否真的存在",其次才查代码逻辑。
2. **排查要有证据链意识**：APK 解剖（ScriptingAssemblies.json 证明 dll 注册 OK）+ 官方文档（非 AB 场景必丢）+ 现象对账（棋盘=代码生成、按钮=绑定）三路交叉,才敢对架构动刀;而不是反复"改代码→打包→试"。
3. **热更架构下,序列化边界就是红线**：热更代码可以写逻辑,但**凡进入序列化管线（场景/prefab）的必须是 AOT 类型**。桥模式把"挂载"留给 AOT、把"逻辑"留给热更,是 HybridCLR 官方认可的唯一无限制组合。
4. **元数据一致性是 Consistent 模式的隐形契约**：改了 AOT 白名单代码,远程 AOT metadata 与包内 strip 产物必须同步重建——构建流水线要把 GenerateContent 放进"改 AOT 代码"的必经步骤。
5. **设备缓存是最后一个"假 bug"来源**：内容重建后行为不变,先查服务器日志确认请求真的到达,再查 UnityWebRequest 磁盘缓存,最后才是代码。
