# 真机性能体检（工具 + 口径）

> 触发方式：**按需**。用户说"体检/跑一下性能/对比下新包"时才执行，不做日常例行。
> 数据留存于 `Build/Logs/perf/`（git 忽略，不入库），供跨版本回归对比与面试复盘。

## 一、工具用法

```bash
# 1. 采集一轮（游戏需先开到手机前台；播放游玩提示时正常操作游戏）
python tools/perf_probe.py probe --tag <标签> [--duration 12] [--pkg com.lixingames.rovilo]

# 2. 列出历史运行
python tools/perf_probe.py list

# 3. 对比两个运行（新包 vs 旧基线），输出 Δ 与 ✅/⚠️/🔴 判定
python tools/perf_probe.py compare Build/Logs/perf/<A> Build/Logs/perf/<B>

# 4. 重生成某目录报告（raw 原始文件在，随时可离线复核）
python tools/perf_probe.py report Build/Logs/perf/<目录>
```

产物：每轮一个目录 `Build/Logs/perf/<tag>_<时间戳>/`，含

- `raw/` 原始抓包：`meta.json`、`battery_start/end.txt`、`mem_start/end.txt`、`top_threads.txt`、`sf_latency.txt`
- `report.md` 人读报告 + `summary.json` 结构化数据（compare 用）

## 二、为什么这么采（指标口径）

| 指标 | 数据源 | 说明 |
|---|---|---|
| 帧率/掉帧 | `dumpsys SurfaceFlinger --latency <图层>` | Unity 走 Vulkan/GL 时 `gfxinfo` 无 HWUI 帧数据（实测空段），SF BufferQueue 时间戳是可靠替代。**限制：只回溯最近 127 帧**（30FPS ≈ 4.2s），采集前先 `--latency-clear`，统计窗口 = min(游玩时长, 127 帧) |
| 主节奏 | 帧间隔 ÷ 刷新周期的众数 | 1=满刷新率；2=锁半速（vSync 双 vblank，即 60Hz 屏跑 30FPS）；3+ 属跑不满 |
| 长帧 | 间隔 > 2.2×刷新周期 | 阈值随 60/90/120Hz 缩放，不写死 40ms |
| 内存 | `dumpsys meminfo` App Summary 段 PSS | 游玩前后各采一次算增量 = 泄漏探针（增量 <30MB 视为无信号） |
| CPU | `top -H` 线程级 ×3 采样 | 取 UnityMain（主线程/脚本+UI）与 UnityGfxDeviceWorker（渲染）均值；两者都不过半说明 CPU 非瓶颈 |
| 温度 | `dumpsys battery` | 十分之一摄氏度；>40°C 提示注意 |
| 省电开关 | `settings get global low_power` | ColorOS 开启时会压刷新节奏，帧率归因前先排除 |

## 三、判定阈值（report/compare 内建）

| 项 | ✅ | ⚠️ | 🔴 |
|---|---|---|---|
| 长帧占比 | 0 | <2%（个别） | ≥2% 需定位环节 |
| 游玩前后 PSS 增量 | <30MB | — | ≥30MB 疑似泄漏 |
| 电池温度 | <40°C | ≥40°C | — |
| compare 平均 FPS | 不降 | 降 1+ 帧 | — |

## 四、2026-09-08 基线（dev/phase9 Debug 包 · OPPO PFFM20）

首次完整体检建立基线，此后新包一律与它同口径对比：

| 项 | 值 |
|---|---|
| 环境 | dev/phase9 Debug APK · IL2CPP · 1440×3216 @60Hz · 用户在旁正常游玩采样 |
| 平均 FPS | 30.0（锁半速 vSync×2；主线程 18.8%/渲染 7.6% 远未饱和，判定非性能瓶颈） |
| 帧间隔 | p50 33.30ms · p95 33.39ms · max 33.50ms · 长帧 0（零掉帧） |
| TOTAL PSS | 458MB（Native Heap 52 + Code 145 + Private Other 196 + System 37） |
| CPU | UnityMain 18.8% / UnityGfxDeviceWorker 7.6%（单核制均值/3 采样） |
| 温度 | 37.0°C |
| 判定 | 游玩前后 PSS 增量 -2.3MB 无泄漏；零掉帧；30FPS 对该点按品类可接受且省电 |

基线目录：`Build/Logs/perf/dev-phase9-baseline_20260908-233502`（用 `list` 查最新）。

采集纪律（首轮踩坑）：**倒计时期间人必须在场游玩**——无人交互时手机若停在特定画面，
可能采到降速样本（首轮曾误采 15FPS 全红样本，作废重采后恢复 30FPS）。
无效样本直接删除运行目录，不留入 compare 池。

## 五、操作流程（用户要求体检时）

1. 确认手机连接且游戏**前台运行**；
2. `python tools/perf_probe.py probe --tag <本次标签>`（新包标签建议 `release-v15`、`dev-phase9` 等，与版本对应）；
3. 采集倒计时期间**提示用户正常游玩**（点格子/切页/看动画）；
4. 完成提示后 `compare` 新旧两轮，按第三节约定的阈值下结论，重点说明：帧节奏是否变化（锁半速或 60 恢复）、内存增量、长帧来源（场景切换/加载瞬间属可接受）；
5. 结果不默认提交 git（产物已忽略），必要时口头汇报口径：帧率/内存/温度三维度。

## 六、已知注意点

- Debug 包比 release 包偏慢偏肥，**对比必须同构建类型**（Debug vs Debug / Release vs Release），跨类型对比结论不可信；
- SF 图层句柄每次会话变化，工具实时发现图层，无需人工参数；
- 采集需要游戏在渲染（前台），后台/熄屏时无帧数据；
- 首测手抓数据（`Build/Logs/perf-meminfo.txt` 等散档）已被工具化产物取代，仅留作 2026-09-08 手工过程存档。
