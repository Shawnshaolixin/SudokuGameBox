## 1. 一句话定位

> 一个**数独游戏盒子**:以「大厅 + 数独 + 井字棋」起步(D-4),多玩法共享一套运营中枢(Trait 开关 + 统一货币 `box.coins`),通过「广告 + 去广告内购」混合变现,主打欧美市场。**v1.0 为自包含纯 AOT 盒子**(极简、无骚扰广告、完整离线、零热更合规风险),v1.1 起启用远程热更上新玩法。

**工作标题(Working Title):** `SudokuGameBox`(与仓库同名,长期可用)

## 2. 关键决策摘要(Executive Summary)

| 决策项 | 结论 | 理由 |
|---|---|---|
| 商业模式 | Free-to-Play + 混合变现(广告 + IAP) | 休闲解谜类用户付费意愿低,广告是主要收入来源;去广告 IAP 提升留存与口碑 |
| 当前执行基线 | **Unity `6000.3.20f1`(国际版)**(C# / IL2CPP) | 2026-08-20 定版(11 号 D-12);旧基线 `2022.3.50f1c1`(中国版 c1)在迁移验收通过前保留 |
| 引擎升级策略 | 已在 P-1 完成 2022.3 → 6000.3 迁移(副本验证后切换) | 工程规模最小的时刻迁移最便宜;迁移 checklist 见 11 号 §4.9 |
| 目标市场 | 英语五国优先(US/UK/CA/AU),次选 EU/JP/KR | 高 eCPM、高付费、数独文化成熟 |
| 差异化 | 首期先做干净盘面、局内无强制广告、完整离线和稳定闭环 | 先把体验和流程打磨好,再补讲解式提示与长线功能 |
| 账号系统 | 首期 **不做自有账号**,也不强依赖 GPGS | 大幅降低合规和接入复杂度 |
| 后端 | 无自建服务器 | 单人开发先避免运维负担,每日挑战和 Remote Config 后置 |
| 热更新 | **v1.0 纯 AOT 自包含上架**;程序集按盒子方案拆分,远程热更 v1.1 起启用 | 首版不下载任何代码 = 零合规风险、零解释执行开销;拆分先做好,后续切换零改动。详见 [11_Unity游戏盒子架构方案.md](./11_Unity游戏盒子架构方案.md) §0 D-2 |
| 盒子化(大厅 + 多玩法) | 以 11 号方案为准,并受数据门控约束 | 多玩法提升留存的假设需先用 v1.0 数据验证(11 号 §12.3) |
| 数据定位 | 不含儿童受众(不选 Families),避免 COPPA 额外义务 | 降低合规成本 |

## 4. 商业假设(需用数据验证)

1. **假设 H1**:数独核心玩家能接受「完成一局后 1 次插屏广告」,前提是局内零广告。
2. **假设 H2**:「逻辑讲解式提示」能显著提升新手留存(D1/D7),形成差异化。
3. **假设 H3**:每日挑战 + 连续签到(Streak)能把 D7 留存从行业基准 ~8% 提升到 12%+。
4. **假设 H4**:去广告一次性买断(定价 $3.99~$4.99)转化率 ≥ 2%。

> 首期 MVP 不以这些假设全部达标为上线门槛,而是先完成可玩、可测、可发布、可复盘的最小闭环。

## 6. 术语约定

- **MVP / Must / P0**:首版必须上线,否则不发布
- **P1 / Should**:软启动后尽快补齐
- **P2 / Could**:全球发布后按数据决定
- **DoD(Definition of Done)**:完成标准,功能「完成」的判据
- **GPGS**:Google Play Games Services(成就/排行榜/云存档)
- **UMP**:Google User Messaging Platform(欧盟/英国 GDPR 同意管理)
- **IAP**:In-App Purchase(应用内购买)
- **ASO**:App Store Optimization(应用商店优化)
